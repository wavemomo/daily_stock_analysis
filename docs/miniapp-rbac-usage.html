当前页面能力：已提供可视化权限管理

小程序会根据当前 Bearer 会话中的 permissions 控制页面入口、菜单和编辑能力；每个后端请求仍会再次进行权限校验。

管理员入口

拥有 rbac.manage 的用户会在“我的”页面看到“权限管理”。进入 pages/rbac/index 后可查询用户、替换角色、启停账号、管理自定义角色及查看审计记录。

三层访问控制

菜单按权限过滤；小程序路由策略要求 rbac.manage 并在每次显示时刷新 /me；所有管理 API 最终由服务端 require_permission('rbac.manage') 校验。隐藏入口不是安全边界。

数据最小化

用户目录只返回用户 ID、展示资料、启用状态、角色和有效权限；不会返回 OpenID、UnionID、Bearer token、token hash 或微信 session_key。

角色与权限模型

角色可以组合，最终权限为所有角色权限的并集。微信用户首次登录默认获得 member；实际执行时以后端 src/services/rbac_service.py 中的权限目录为准。

member · 普通成员

新用户默认角色。可维护本人会话、心得、持仓、告警与 Agent 会话；读取股票、决策信号、情报，并执行 Agent 对话。

operator · 运营分析员

受信任运营角色。除 system.manage 和 rbac.manage 外拥有全部权限，可执行共享计算、维护共享资源并发送告警。

admin · 管理员

拥有全部权限，包括系统维护 system.manage 与用户授权 rbac.manage。

RBAC 决定“是否可使用某项能力”；资源归属决定“可访问哪一位用户的数据”。例如管理员权限不应让普通用户的心得、持仓或 Agent 会话越权可见；个人资源仍由服务端按当前登录用户隔离。

添加第一位管理员：受控角色授予

目标用户必须先完成一次微信登录，由受控运维流程向现有用户授予 admin 或包含 rbac.manage 的角色并记录审计事件。首位管理员可用后，日常授权统一在“我的 → 权限管理”完成。

  1. 完成微信后端配置。在服务器部署环境配置 WECHAT_MINIAPP_APP_ID 与 WECHAT_MINIAPP_APP_SECRET；密钥只能存在后端，绝不能写入小程序代码。
  2. 让目标管理员先登录一次小程序。后端会创建用户及默认 member 角色。
  3. 通过受控运维流程确认目标用户。使用内部受保护的用户管理边界，避免在前端、日志、群聊或工单传播 OpenID、UnionID、Bearer token 或会话信息。
  4. 执行一次性角色授予并保存审计记录。验证该用户重新登录后，GET /api/v1/miniapp/auth/me 返回预期的 roles 与 permissions。
不要配置自动回授白名单：管理员资格必须是可审计的显式角色关系。回收角色后，应通过权限管理页或受控运维流程完成，并验证至少另一位拥有 rbac.manage 的活跃用户可用。

权限管理页面与自动化 API

日常管理入口为“我的 → 权限管理”（pages/rbac/index）。仅拥有 rbac.manage 的管理员可见、可进入并可调用以下 API；菜单过滤、路由门禁和后端 require_permission('rbac.manage') 同时生效。认证头使用小程序登录后签发的 Bearer token。

页面可以完成的操作

用户目录

按昵称或用户 ID 搜索、分页查看用户、有效角色与权限，并启用或停用账号。目录不暴露 OpenID、UnionID、token 或 session_key。

角色替换

为用户提交完整角色集合。至少保留一个角色；系统拒绝未知角色、移除当前操作者的 rbac.manage，以及停用或降权最后一位拥有该权限的活跃用户。

自定义角色

创建、更新和删除数据库中的自定义角色及其有效权限码。member、operator、admin 是系统角色，只读且不可在页面编辑或删除。

审计记录

查看用户角色变更、账号状态变更和自定义角色生命周期的时间、操作者及非敏感元数据，便于追溯高权限操作。

API 一览

方法与路径用途关键约束
GET /rbac/catalog读取有效权限目录和全部角色。权限码以服务端代码为唯一真源。
GET /rbac/users?query=&page=&page_size=分页查询安全用户目录。每页 1–100 条；不返回身份或会话密钥。
PUT /rbac/users/{id}/roles替换目标用户全部角色。不是追加；至少一个已存在角色；按有效 rbac.manage 权限保留管理能力保护。
PATCH /rbac/users/{id}/active启用或停用目标用户。不能停用自己或最后一位拥有 rbac.manage 的活跃用户。
POST /rbac/roles创建自定义角色。角色码、名称、描述及权限均校验。
PUT /rbac/roles/{code}更新自定义角色与权限。系统角色不可修改。
DELETE /rbac/roles/{code}删除未分配的自定义角色。仍被用户分配的角色会被拒绝删除；成功返回 204。
GET /rbac/audit?page=&page_size=分页读取权限管理审计记录。只含角色、状态等非敏感管理元数据。

角色替换示例

curl -sS -X PUT "$BACKEND_BASE_URL/api/v1/miniapp/rbac/users/$TARGET_USER_ID/roles" \
  -H "Authorization: Bearer $ADMIN_BEARER_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"roles":["member","operator"]}'
这是“替换”，不是“追加”。请求体中的 roles 会成为该用户新的完整角色集合。要保留已有角色，必须把所有待保留角色一起提交；空集合、未知角色、不存在的用户以及破坏管理员保护的操作均会被拒绝。

操作前检查清单

  • 优先通过管理页面选择正确用户；API 自动化时，再确认 TARGET_USER_ID 与目标一致。
  • 把 Bearer token 当作密码处理：仅在受控终端临时使用，不写进脚本、文档、截图或版本库。
  • 先验证至少两位管理员（含一位 break-glass 账号）均可登录和授权，再回收高权限角色或停用账号。
  • 系统角色由后端启动时同步，升级时会恢复其标准权限集合；需要组织特有权限组合时，请创建自定义角色，而不是修改系统角色。

安全边界与运维原则

前端不是安全边界

菜单隐藏、按钮禁用和路由门禁只改善体验。后端的 Bearer 认证、require_permission() 与资源 owner 过滤才是最终安全控制。

401 与 403 的含义

401 表示未登录或会话失效；403 表示已登录但缺少权限。不要把两者都当成“网络错误”。

会话可撤销

后端只保存随机 Bearer token 的 SHA-256 摘要，登出会撤销当前会话。不要将原始 token 写入日志。

最小权限

优先使用 member；仅在需要共享运维能力时授予 operator；仅把 admin 分配给实际需要授权与系统维护的人员。

微信登录：页面展示与安全流程

当前登录页会在状态区下显示“将使用微信登录”或“已使用微信登录”。这表示身份认证使用微信官方登录能力，而不是额外的系统密码。

01小程序调用 wx.login获取一次性临时 code。
02code 发给本项目后端只发送给配置的业务服务器。
03后端调用 code2session用 AppID/AppSecret 与微信交换身份信息。
04后端建立本地会话创建或更新用户、解析 RBAC 并签发 Bearer token。
05后续请求携带 Bearer后端逐次校验会话、权限与资源归属。

登录页实际会展示什么

  • 认证进行中：显示“将使用微信登录”，并提示正在连接微信账号。
  • 认证完成：显示“已使用微信登录”，并提示身份已通过一次性凭证验证。
  • 资料引导：认证成功后，用户可主动选择头像或填写微信昵称，也可以跳过；这些展示资料不参与身份、权限或数据归属。
  • 认证失败：显示失败原因与“重新登录”按钮，不会降级为匿名访问。
重要：微信的临时 code 只能使用一次。session_key 仅用于服务端处理加密数据，不能回传给小程序，也不能对外提供。当前系统不会在页面加载时静默获取头像和昵称，只有用户主动触发资料填写时才使用对应的微信官方能力。

常见问题

为什么登录后仍看不到某个页面？
先检查 GET /api/v1/miniapp/auth/me 返回的 roles 与 permissions，再确认该页面的最低权限要求。隐藏入口不代表后端会放行；缺权限请求会返回 403。
为什么首次管理员没有自动出现？
管理员资格不再由 OpenID 配置自动授予。先确认目标用户已完成微信登录，再由受控运维流程对该用户执行一次性角色授予并写入审计；随后通过 GET /api/v1/miniapp/auth/me 核对 roles 与 permissions。
可以直接把 AppSecret 放进小程序配置吗？
不可以。AppSecret 必须只保存在后端环境变量；小程序只获取临时 code，并把 code 交给业务后端。
移除一个管理员为什么被拒绝？
系统按有效的 rbac.manage 权限保护最后一位活跃管理者，而不只按 admin 角色名称判断。请先验证至少另一位可管理用户可用，再执行角色替换或停用操作。
可以直接在小程序中为其他用户授权吗？
可以，但仅限拥有 rbac.manage 的管理员。在“我的 → 权限管理”中可搜索用户、替换角色、启停账号、配置自定义角色并查询审计记录；页面不可见、路由门禁和后端 API 都会拒绝无权限访问。
